## 1. Сначала диагностика

Схему меняют только после того, как понятно, на каком уровне ломается доступ. Один и тот же симптом «не работает» бывает следствием совсем разных причин.

| Что наблюдается | Где искать | Чем подтвердить |
| --- | --- | --- |
| По IP ресурс открывается, по имени — нет | разрешение DNS | сравнить ответ DNS провайдера и зашифрованного резолвера (DoH/DoT) |
| TCP-соединение устанавливается, TLS-рукопожатие рвётся | фильтрация по SNI или проблема сертификата | `openssl s_client` с разными значениями `-servername` |
| Мелкие запросы проходят, долгие загрузки замирают | ограничение скорости длительных соединений или MTU | тот же адрес с другого провайдера или VPS; проверка MTU (skill `network`) |
| TCP работает, UDP и QUIC — нет | фильтрация UDP | клиент в режиме только TCP |
| Зарубежный VPS недоступен, VPS в своей стране — доступен | политика по направлению или адресу | путь через промежуточный VPS |
| Прокси работает, но отдельный сайт отказывает | репутация или страна выходного IP | выход для этого сайта через другой адрес (раздел 6) |
| С одного устройства работает, через роутер — нет | прозрачное проксирование, петля маршрутов, DNS | сначала проверка через SOCKS (раздел 7) |

Для каждого теста записывать сеть и провайдера, место, время, протокол, направление и версию клиента. Вывод о поведении «всей страны» по одному провайдеру или одному замеру не делать.

## 2. Варианты топологии

| Схема | Когда уместна | Что даёт | Чем платим |
| --- | --- | --- | --- |
| Клиент → зарубежная Node | прямой путь стабилен | минимум компонентов, проще всего чинить | весь трафик зависит от доступности одного зарубежного адреса |
| Клиент → промежуточный VPS → зарубежная Node | прямой путь деградирует или блокируется | другой первый участок пути, можно добавить резерв | дополнительная задержка и ещё один сервер |
| Каскад + выход через WARP для части сайтов | отдельные сервисы отвергают адрес VPS | совместимость с этими сервисами | ещё одна зависимость; только для выбранных доменов |
| Роутер → каскад | много устройств или устройства без клиента | не нужен клиент на каждом устройстве | ресурсы роутера, сложная маршрутизация |
| Клиент → CDN → origin | edge CDN доступен, а прямой адрес — нет | другой вход в сеть, TLS по настоящему домену | домен, сертификаты, ограничения CDN по транспортам; Reality не подходит |

Начинать с прямой схемы: она служит контрольной точкой, даже если в итоге понадобится сложнее. Каждое следующее звено добавлять, только когда диагностика показала, зачем оно нужно.

## 3. Прямой вход на Node

Базовая схема на Remnawave:

- сервер с поддерживаемым Linux (docs Remnawave рекомендуют Ubuntu или Debian), Remnawave Node установлена по официальной инструкции; Xray-core работает внутри контейнера Node;
- inbound описан в Config Profile на Panel; для прямого пути типичен VLESS с `security: reality`;
- порт `443`, если он свободен;
- для Reality в inbound задаются `target` (адрес и порт реального TLS-сайта; в старых версиях и гайдах поле называлось `dest`, сейчас оба имени — синонимы, в новых конфигурациях использовать `target`), `serverNames` (имена, которые принимает сервер; документация Xray советует брать их из SAN сертификата `target`), `privateKey` (пара ключей генерируется командой `xray x25519`) и `shortIds`;
- outbounds `freedom` (прямой выход) и `blackhole` (блокировка).

Выбор транспорта поверх Reality (TCP с Vision, XHTTP и другие) зависит от поддержки сервером и клиентами; документация Xray описывает варианты, но не называет один из них лучшим для всех сетей.

Проверки на Node (каталог `/opt/remnanode` — из официальной инструкции; для нестандартной установки — skill `remnawave`):

```bash
ss -lntup
cd /opt/remnanode && docker compose ps
docker compose logs --since 10m
docker exec remnanode xlogs
```

Клиентам параметры подключения (UUID, адрес, порт, транспорт, ключ, SNI, short ID) отдаёт подписка Remnawave по данным Config Profile и Hosts. Ссылка подписки — секрет. Настройка Config Profiles, Hosts и Squads — skill `remnawave`.

## 4. Защита панели

До того как панель станет доступна извне:

- только HTTPS через reverse proxy; docs Remnawave запрещают публиковать сервисы напрямую;
- уникальные надёжные учётные данные администратора; вход по passkey или OAuth, если он настроен;
- ограничить доступ к панели: firewall по адресам, приватная административная сеть или Cloudflare Tunnel с Access (skill `cloudflare`), либо дополнительные слои из раздела Panel Security docs Remnawave;
- регулярные резервные копии базы и конфигурации.

Старые скрипты установки и названия полей интерфейса из сторонних статей могут не соответствовать текущей версии; ориентир — актуальная документация.

## 5. Каскад через промежуточный VPS

Три способа связать промежуточный сервер с зарубежным, от простого к сложному.

### 5.1. Перенаправление средствами ядра (iptables)

Подходит, когда один порт промежуточного сервера нужно без изменений передать на один зарубежный адрес. Трафик не расшифровывается, нагрузка минимальна.

Порядок:

1. Убедиться, что есть резервный доступ к серверу помимо SSH (консоль провайдера).
2. Сохранить текущие правила: `iptables-save > /root/iptables.backup`.
3. Включить пересылку пакетов на постоянной основе (`net.ipv4.ip_forward = 1` в `/etc/sysctl.d/`).
4. Разрешить loopback, уже установленные соединения, SSH и порт перенаправления.
5. Добавить правило DNAT в таблицу `nat` (цепочка `PREROUTING`) для нужного порта на зарубежный адрес; UDP — только если он нужен транспорту.
6. Добавить `MASQUERADE` (цепочка `POSTROUTING`) и разрешающие правила в `FORWARD` только для этого направления.
7. Политику по умолчанию ужесточать последней и проверять доступ из второй SSH-сессии, не закрывая первую.
8. Сохранить правила так, чтобы они пережили перезагрузку, и проверить это перезагрузкой.

Чужие правила на рабочем сервере не сбрасывать целиком; при замене опираться на сохранённую копию.

### 5.2. HAProxy в режиме TCP

Подходит, когда нужны проверки доступности бэкендов, несколько зарубежных серверов или балансировка.

- `mode tcp` в `frontend` и `backend`: HAProxy пересылает поток, не разбирая TLS.
- Явные `timeout connect`, `timeout client`, `timeout server`.
- Параметр `check` у серверов бэкенда включает проверки доступности.
- Алгоритм `balance` выбирать под нагрузку: `roundrobin`, `leastconn` для длинных соединений, `source` для привязки клиента к серверу.
- Страницу статистики, если она нужна, слушать только на `127.0.0.1` или в административной сети.
- Без дополнительных настроек зарубежная Node видит адрес HAProxy, а не клиента: лимиты по IP и журналы подключений склеивают всех пользователей в один адрес. HWID device limit от этого не зависит: Remnawave считает устройства по заголовкам клиента при запросе подписки, а не по адресу подключения. Чтобы передать реальный адрес клиента, включить PROXY protocol: в HAProxy — параметр `send-proxy-v2` у строки `server`, на inbound Xray в Config Profile — `acceptProxyProtocol: true` в настройках транспорта. После этого inbound закрывает любое соединение без PROXY-заголовка, поэтому все клиенты этого inbound должны приходить только через HAProxy.

Перед применением:

```bash
haproxy -c -f /etc/haproxy/haproxy.cfg
systemctl reload haproxy
```

### 5.3. Промежуточная Node с Xray

Подходит, когда промежуточный сервер должен сам решать, куда отправить трафик: например, российские сайты — напрямую, остальное — на зарубежную Node. В Remnawave это схема server-side routing (bridge) из docs; как её собрать — skill `remnawave`.

Что учесть:

- у клиентов и у связи «промежуточная → зарубежная» разные учётные данные;
- у outbounds понятные уникальные теги (например, `DIRECT`, `BLOCK`, outbound на зарубежную Node);
- Xray проверяет правила маршрутизации сверху вниз и применяет первое совпавшее, поэтому частные правила (`geosite:…`, `geoip:…`) идут выше общего правила на зарубежную Node; трафик, не попавший ни под одно правило, уходит в первый outbound списка;
- для маршрутизации по доменам на inbound нужен sniffing (`destOverride`: `http`, `tls`, `quic`);
- каждая категория geosite и geoip — отдельная запись в правиле.

Цена: промежуточный сервер расшифровывает и снова шифрует трафик, это нагрузка на CPU, дополнительная задержка и ещё одно место, где клиентский отпечаток TLS может отличаться от ожидаемого. Если маршрутизация по доменам не нужна, проще варианты 5.1 и 5.2.

## 6. Выборочный выход через WARP

Если отдельные сайты отвергают адрес зарубежного VPS, трафик только к этим сайтам можно выпускать через Cloudflare WARP на том же сервере.

1. Установить клиент из официального репозитория пакетов Cloudflare (`pkg.cloudflareclient.com`), пакет `cloudflare-warp`.
2. Зарегистрировать клиент: `warp-cli registration new`.
3. Перевести клиент в режим локального прокси (список режимов — `warp-cli mode --help`). В этом режиме клиент слушает SOCKS на `127.0.0.1`, порт по умолчанию `40000`, и пропускает только тот трафик, который явно направлен в прокси.
4. Подключить: `warp-cli connect`.
5. Проверить через прокси: в ответе `curl --socks5-hostname 127.0.0.1:40000 https://www.cloudflare.com/cdn-cgi/trace` должна быть строка `warp=on`.
6. В Config Profile добавить outbound `socks` на `127.0.0.1:40000` (Remnawave Node работает с `network_mode: host`, поэтому адрес хоста доступен из контейнера) и правило маршрутизации, которое отправляет в него только нужные домены.
7. Убедиться, что весь остальной трафик по-прежнему уходит через `freedom`.

Синтаксис `warp-cli` менялся между версиями; при расхождении источник истины — текущая документация Cloudflare. Весь трафик через WARP не направлять без явной задачи: это меняет выходной адрес для всех пользователей Node.

## 7. Прозрачное проксирование на роутере

Нужна, когда клиент нельзя поставить на каждое устройство. Пошаговая настройка конкретных прошивок в этот справочник не входит; ниже правила, общие для любой реализации.

Из прозрачного проксирования исключать:

- адрес сервера, к которому подключается сам роутер, иначе туннель попадёт сам в себя;
- локальные сети и адреса самого роутера;
- loopback, multicast, broadcast и пути управления роутером;
- любые адреса, нужные для установки туннеля (например, DNS для разрешения имени сервера).

Прежде чем включать прозрачный режим, проверить путь через SOCKS:

```bash
curl https://ifconfig.me
curl --socks5-hostname 127.0.0.1:1080 https://ifconfig.me
```

Первый адрес — выход провайдера, второй — выход через прокси. Признаки выявления роутерной схемы — skill `detection-audit`.

## 8. Вход через CDN

CDN маршрутизирует соединение по настоящему доменному имени и завершает TLS у себя. Поэтому через CDN проходят только транспорты поверх HTTP(S) с настоящим доменом, а Reality, которому нужно собственное рукопожатие с сервером, не проходит.

Типовой путь для Cloudflare:

```text
клиент или промежуточный VPS
  -> edge CDN (TLS, порт 443)
  -> nginx на origin с валидным сертификатом
  -> 127.0.0.1 или Unix socket
  -> Xray: VLESS поверх WebSocket или gRPC, без собственного TLS
```

Требования:

- домен подключён к CDN, DNS-запись в режиме `Proxied`;
- на origin валидный сертификат, режим SSL/TLS `Full (strict)`;
- в настройках зоны включены нужные функции: WebSocket работает на любом HTTPS-порту из списка Cloudflare, gRPC — только на `443`; XHTTP Cloudflare отдельно не подтверждает (skill `cloudflare`);
- nginx передаёт в Xray только секретный путь, на остальные запросы отвечает обычным сайтом или стандартной ошибкой;
- Xray слушает `127.0.0.1` или Unix socket. В Remnawave Xray работает внутри контейнера Node с `network_mode: host`, поэтому `127.0.0.1` доступен nginx на хосте без дополнительных настроек; Unix socket должен лежать в каталоге, смонтированном в контейнер Node и доступном nginx;
- клиент использует `security=tls`, настоящий домен как SNI и Host и тот же путь.

Проверка:

```bash
nginx -t
curl -I https://example.com/
openssl s_client -connect example.com:443 -servername example.com
```

Если DNS позволяет, проверять прямой путь к origin и путь через CDN по отдельности.

## 9. Базовая безопасность серверов

Инженерная практика, общая для всех схем:

- SSH только по ключам; вход по паролю и под root отключать после того, как проверен резервный доступ; при изменениях firewall держать вторую сессию открытой;
- обновлять систему, не фиксировать устаревшие репозитории пакетов;
- слушать только нужные адреса, открывать в firewall только нужные порты;
- для каждого участка цепочки и каждого клиента — свои случайные учётные данные;
- утёкшие UUID, ключи, пароли, ссылки и сертификаты перевыпускать;
- не оставлять ссылки подписок в логах, скриншотах, тикетах и истории shell;
- сторонние установочные скрипты читать перед запуском, предпочитать закреплённые версии и проверку контрольных сумм;
- резервные копии конфигураций хранить с правами `0600`;
- статистику, административные интерфейсы, SOCKS и DNS не публиковать наружу;
- учитывать условия провайдера и местное законодательство.

## 10. Приёмка и разбор отказов

### Проверка по слоям

После каждого изменения проверять по порядку:

1. Сервис запускается без ошибок конфигурации.
2. Нужный порт слушает нужный адрес.
3. Клиент проходит рукопожатие транспорта и TLS/Reality.
4. Внешний IP через прокси совпадает с задуманной точкой выхода.
5. Выбранные домены уходят через задуманный outbound.
6. Остальные домены идут напрямую там, где настроена раздельная маршрутизация.
7. DNS разрешается задуманным резолвером и возвращает рабочие A/AAAA.
8. TCP и UDP ведут себя так, как задумано.
9. Схема переживает перезагрузку.
10. Откат возвращает исходный доступ.

### Типовые отказы

| Отказ | С чего начать |
| --- | --- |
| Соединение сразу отклоняется | слушает ли сервис, firewall, правильность адреса и порта |
| Ошибка TLS | SNI, цепочка сертификатов, время на сервере, режим SSL/TLS в CDN |
| Не проходит рукопожатие Reality | `target` и `serverNames`, ключи, short ID, отпечаток TLS клиента |
| Через SOCKS работает, прозрачно — нет | правила nftables, метки пакетов, таблица маршрутов, исключения против петли |
| Правило по домену не срабатывает | sniffing, `domainStrategy`, порядок правил, данные geosite |
| CDN отвечает HTTP-ошибкой | Host и путь, заголовки WebSocket или gRPC, слушает ли origin |
| После правки firewall пропал SSH | порядок правил и политика `INPUT`, реальный порт SSH, консоль провайдера |
| Высокая нагрузка или задержка | двойное завершение TLS, мощность роутера, выбор транспорта |
| Часть приложений идёт мимо политики | IPv6, QUIC/UDP, встроенный в приложение DNS, certificate pinning |

Если смена отпечатка TLS клиента по наблюдениям помогает, фиксировать это как наблюдение с версией клиента и датой, а не как универсальное решение.
