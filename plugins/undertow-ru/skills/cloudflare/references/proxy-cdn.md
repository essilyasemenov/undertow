# Cloudflare Proxy CDN

Стандартный прокси и CDN Cloudflare для веб-трафика.

## Базовая модель

- Термины `Proxied`, `DNS only`, edge и origin определены в [SKILL.md](../SKILL.md); здесь — поведение стандартного прокси Cloudflare, когда имя уже `Proxied`.
- Стандартный прокси Cloudflare работает для HTTP/HTTPS, а не для произвольного TCP/UDP-трафика.
- Кэширование, WAF и часть функций производительности и безопасности применяются, только когда имя действительно `Proxied`.
- Origin должен понимать, что за Cloudflare может стоять реальный клиентский IP и цепочка прокси-заголовков.

## Что проверять в первую очередь

1. Proxy status имени.
2. Поддерживает ли стандартный прокси этот порт.
3. Нужен ли кэш вообще или требуется bypass.
4. Есть ли WebSocket или gRPC и включён ли он в настройках зоны.
5. Как origin восстанавливает реальный IP клиента.

## Поддерживаемые порты

По умолчанию Cloudflare проксирует только эти порты:

| Протокол | Порты |
| --- | --- |
| HTTP | 80, 8080, 8880, 2052, 2082, 2086, 2095 |
| HTTPS | 443, 2053, 2083, 2087, 2096, 8443 |

- На портах 2052, 2053, 2082, 2083, 2086, 2087, 2095, 2096, 8880 и 8443 кэширование выключено; включить его можно только на Enterprise через cache rule.
- Для другого порта два пути: сделать hostname `DNS only` или использовать Spectrum. Spectrum для всех TCP/UDP-портов есть только на Enterprise.
- На непроксируемых портах edge может принять TCP-соединение, но HTTP/HTTPS-запросы до origin не дойдут.

## WebSocket и gRPC

- WebSocket включается на странице **Network** зоны (переключатель **WebSockets**) или через API-настройку `websockets`.
- gRPC включается там же (переключатель **gRPC**). Требования Cloudflare:
  - endpoint слушает порт 443;
  - поддерживает TLS и HTTP/2, HTTP/2 объявлен через ALPN;
  - `Content-Type` запросов — `application/grpc` или `application/grpc+<тип>`;
  - hostname `Proxied`, SSL/TLS mode не ниже `Full`.
- Через Cloudflare Tunnel gRPC поддерживается только в private subnet routing, не через public hostname.

## Заголовки origin-side

- `CF-Connecting-IP` — предпочтительный заголовок для получения исходного IP клиента на origin.
- `X-Forwarded-For` — цепочка IP-адресов через прокси, а не один стабильный адрес.
- `X-Forwarded-Proto` показывает, по какому протоколу клиент пришёл к Cloudflare.

## Практические правила

- Если приложение ведёт аудит, rate limiting или access control по IP, сначала определить, какой заголовок оно должно читать.
- Для origin-логов обычно полезнее `CF-Connecting-IP`, чем разбор цепочки `X-Forwarded-For`.
- Для WebSocket проверять, что приложение действительно работает через WebSocket и укладывается в поддерживаемый Cloudflare веб-трафик.
- Если сервис слушает нестандартный порт, сначала сверять его со списком портов выше.

## Кэширование

- Не считать кэш Cloudflare включённым и полезным «по умолчанию для всего».
- Разделять задачи CDN, правил кэширования (cache rules) и доступности через reverse proxy.
- Если важна свежесть данных или поведение API, сначала проверить, нужен ли обход кэша (cache bypass) или отдельные правила.

## Что не делать

- Не описывать прокси Cloudflare как замену TCP-балансировщика.
- Не подменять `CF-Connecting-IP` произвольным разбором `X-Forwarded-For`, если задача — получить исходный клиентский IP.
- Не обещать кэширование на любом порту или для любого протокола.
