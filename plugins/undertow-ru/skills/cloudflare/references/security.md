# Cloudflare Security

Защита веб-приложения, API или origin на стороне Cloudflare.

## Актуальная терминология

- В текущей документации Cloudflare прежние `Firewall Rules` устарели (deprecated) и переведены в `WAF custom rules`.
- Для новых решений ориентироваться на `WAF`, `Custom rules`, `Managed rules`, `Rate limiting rules` и `DDoS Protection`.

## Базовые компоненты

- `WAF`: проверяет входящий HTTP- и API-трафик и применяет наборы правил.
- `Custom rules`: собственная логика фильтрации с действиями вроде `Block` и `Managed Challenge`.
- `Managed rules`: готовые наборы правил Cloudflare.
- `Rate limiting rules`: ограничение частоты запросов по выражению и характеристикам клиента.
- `Bot protection`: защита от нежелательных ботов и связанные с ней правила.
- `DDoS Protection`: автоматическая защита на уровнях L3/L4/L7 на стороне Cloudflare.

## Рабочий процесс

1. Определить тип угрозы: эксплуатация уязвимостей, подбор паролей, парсинг, нежелательные боты, объёмная атака, злоупотребление API.
2. Разделить готовую защиту (managed) и собственную логику (custom).
3. Новые HTTP-политики формулировать в терминах custom rules и языка правил.
4. Для злоупотреблений, которые видны по частоте запросов, использовать rate limiting rules.
5. Для сценариев, чувствительных к нагрузке на origin, проверять, доходит ли вредный трафик до origin или отсекается на edge.

## Практические правила

- Если пользователь просит «firewall rules», объяснять через современную модель `WAF custom rules` и при необходимости упоминать прежний термин.
- Для ботов сначала проверять встроенные возможности защиты от ботов и только потом усложнять собственные правила.
- Для подбора паролей и злоупотребления API rate limiting — отдельный слой, а не замена WAF.
- DDoS-защиту не описывать как ручной переключатель «включить защиту»: у Cloudflare значительная её часть работает автоматически.
- Challenge рассчитан на браузер. Документация Cloudflare Challenges отдельно предупреждает, что interstitial challenge затрагивает API-эндпоинты, к которым ходят не браузеры (`curl`, мобильные бэкенды, server-to-server), а WebView в приложениях может работать ограниченно. Для путей, куда ходят клиентские приложения (например, выдача подписок), challenge-правила проектировать с этим ограничением.

## Что не делать

- Не строить новые рекомендации на устаревших Firewall Rules как на основной модели API и интерфейса.
- Не обещать, что одно custom rule заменит все managed-защиты.
- Не придумывать пороги rate limiting без явной пометки, что это пример, а не правило из документации.
