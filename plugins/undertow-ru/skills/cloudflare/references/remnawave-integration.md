# Cloudflare рядом с Remnawave и homelab

Как встроить Cloudflare в VPN- или homelab-инфраструктуру на Remnawave. Рекомендации остаются строго на стороне Cloudflare, без выдуманных настроек внешних систем.

## Границы этого раздела

- Раздел описывает, как Cloudflare ведёт себя рядом с Remnawave Panel, страницей подписок, Remnawave Node, `Nginx Proxy Manager` и домашними сервисами.
- Как настраивать сами Hosts, Config Profiles и транспорты Xray, решает skill `remnawave`.
- Если для внешнего продукта нет подтверждённой схемы на стороне Cloudflare, это нужно прямо сказать.
- В приоритете архитектурные решения Cloudflare: `DNS only`, `Proxied`, `Tunnel`, `Access`, `Cloudflare One Client`, `Origin CA`, `WAF`.
- Базовая терминология — в [SKILL.md](../SKILL.md), детали — в остальных файлах `references/`.

## Модель

- Remnawave Panel и страница подписок — обычные HTTP(S)-сервисы за reverse proxy на origin; к ним применимы `Proxied`, Tunnel и Access.
- Remnawave Node принимает клиентский трафик Xray. Её нельзя автоматически считать совместимой со стандартным прокси Cloudflare на любом транспорте.
- Домашняя сеть обычно выступает как сеть origin или частная LAN за Tunnel.
- `Nginx Proxy Manager` — reverse proxy на стороне origin, а не функция Cloudflare.
- Если транспорт не является подтверждённым HTTP/HTTPS-трафиком, сначала проверить, не нужен ли `DNS only` или другой продукт Cloudflare.
- На стороне Cloudflare подтверждены WebSocket и gRPC с их требованиями ([proxy-cdn.md](proxy-cdn.md)). Это требования Cloudflare к трафику, а не гарантия совместимости конкретного транспорта Xray. Порты у них разные: WebSocket — любой HTTPS-порт из списка (443, 2053, 2083, 2087, 2096, 8443), gRPC — только 443.
- `XHTTP` не описывать как гарантированно совместимый со стандартным прокси Cloudflare: документация Cloudflare задаёт границы HTTP/HTTPS-прокси, но отдельно XHTTP не подтверждает. Не рекомендовать `Proxied` как готовую настройку XHTTP без подтверждения для конкретной схемы.
- `Proxied`-имя завершает TLS на edge Cloudflare его собственным сертификатом. Вывод (не текст документации Cloudflare): транспорт, которому нужно собственное TLS-рукопожатие клиента с Node, например `Reality`, через стандартный прокси Cloudflare не пройдёт; такое имя — `DNS only`.

## Рабочий процесс

1. Зафиксировать сервис: панель, адрес выдачи подписок, внутренний dashboard, API, частное приложение или транспорт Node.
2. Определить, веб-трафик это или нет.
3. Выбрать модель публикации: `Proxied` для поддерживаемых веб-сценариев; `DNS only` для прямых подключений и транспортов, которые стандартный прокси не поддерживает; `Tunnel` для безопасной публикации без IP origin; `Access` / `Cloudflare One Client` для частного или только административного доступа.
4. Отдельно выбрать режим SSL/TLS и сертификат для origin.
5. Для защиты origin учитывать разрешение входящих только с IP Cloudflare, Authenticated Origin Pulls или Tunnel.

## Практические правила интеграции

- Для `Nginx Proxy Manager`, Caddy или Nginx описывать Cloudflare как внешнюю точку входа (edge), а reverse proxy — как origin.
- Для Remnawave Panel сначала рассматривать Tunnel + Access, а не прямую публикацию: это административный интерфейс.
- Страницу подписок открывают клиентские приложения, а не только браузер. Access-логин и challenge-правила рассчитаны на браузер, поэтому на этом пути они могут сломать обновление подписок (вывод из ограничений в [security.md](security.md)).
- Для домашней сети сначала решить, нужен ли public hostname или частный доступ.
- Для Remnawave Node не утверждать, что любой inbound или транспорт можно пустить через оранжевое облако.
- Если имя указывает на другой CDN или прокси-провайдер, не ставить перед ним прокси Cloudflare без явной совместимости: возможны ошибки TLS, петля маршрутизации или отказ соединения. Для такой записи по умолчанию оставлять `DNS only`.

## Видимость инфраструктуры

Публикация через Cloudflare меняет то, какой IP видит клиент при подключении к Node, но не меняет адрес, с которого Node выходит к сайтам. Как это влияет на признаки выявления, решает skill `detection-audit`.

## Что не делать

- Не придумывать совместимость нестандартного VPN-транспорта со стандартным прокси Cloudflare.
- Не выдавать шаги для NPM или Remnawave за «официальные шаги Cloudflare».
- Не превращать Cloudflare в универсальный ответ на задачи L4/L7 без проверки продукта и транспорта.
