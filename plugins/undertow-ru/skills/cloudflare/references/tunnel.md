# Cloudflare Tunnel

Подключение сервиса к Cloudflare без публикации IP-адреса origin и без входящего порта на маршрутизаторе или межсетевом экране.

## Базовая модель

- `cloudflared` устанавливает только исходящее соединение от origin к Cloudflare.
- Tunnel отвечает за сетевой путь между origin и Cloudflare.
- Вопросы identity, Access policies, Cloudflare One Client и service tokens относятся к [zero-trust.md](zero-trust.md), а не к этому разделу.
- Tunnel не описывать как «обычную A-запись на домашний IP»: это отдельная модель подключения.

## Типовые сценарии

- Публикация self-hosted веб-приложения по публичному имени (public hostname).
- Публикация домашней панели или dashboard (например, Remnawave Panel) без открытия входящего порта.
- Подключение частной сети (CIDR) к Cloudflare через Tunnel.
- Подключение локального сервиса к Cloudflare без прямого входящего доступа к origin.

## Рабочий процесс

1. Определить, что нужно: public hostname или маршрут в частную сеть.
2. Если сервис должен быть доступен из Интернета как веб-приложение, публиковать его через public hostname поверх Tunnel.
3. Если сервис должен быть доступен только авторизованным пользователям или устройствам, сначала спроектировать путь через Tunnel, а затем при необходимости добавить слой из [zero-trust.md](zero-trust.md).
4. Зафиксировать, какой локальный сервис публикуется и по какому протоколу.
5. Проверять Tunnel отдельно от DNS, Access policy и самого приложения на origin.

## Практические правила

- Для домашней лаборатории Tunnel обычно безопаснее, чем публикация IP-адреса origin.
- Для частного доступа через Cloudflare Zero Trust проектировать не только Tunnel, но и отдельный слой политик.
- Если задача — «спрятать домашний origin и не открывать порт», Tunnel рассматривать первым.
- Не смешивать public hostname для доступа из браузера и маршрутизацию частной сети (CIDR): это разные функции Cloudflare Tunnel.
- gRPC через Tunnel поддерживается только в маршрутизации частной сети (private subnet routing); через public hostname не поддерживается.

## Что не делать

- Не описывать Tunnel как требующий публичного маршрутизируемого IP на origin.
- Не путать проксируемую DNS-запись и Tunnel как один механизм.
- Не придумывать настройки ingress, которых нет в официальной документации.
