# DNS

Использовать этот раздел, когда проблема выглядит как "Интернет есть, но сайты по именам не открываются", а также когда нужно объяснить различие между recursive resolver и authoritative nameserver.

## Простое объяснение

DNS переводит доменные имена в IP-адреса. Без DNS человеку пришлось бы помнить IP каждого сервиса.

## Техническое объяснение

DNS - прикладной распределенный и иерархический протокол, стандартизованный в RFC 1034 и RFC 1035. Клиент обычно обращается к рекурсивному резолверу, а тот уже взаимодействует с root, TLD и авторитативными серверами, используя кэш и последовательность запросов.

## История

- DNS пришел на смену централизованным hosts-файлам.
- RFC 1034 и RFC 1035 остаются базовыми документами архитектуры и протокольной формы.

## DNS: подробно

### RFC и нормативная база

- RFC 1034 - Concepts and Facilities
- RFC 1035 - Implementation and Specification
- RFC 2181 - Clarifications to the DNS Specification
- RFC 2308 - Negative Caching
- RFC 7766 - DNS over TCP requirements

### Базовая схема

```text
application
  -> stub resolver
    -> recursive resolver
      -> root
      -> TLD
      -> authoritative server
    <- answer from cache or iterative lookups
```

### Recursive vs Authoritative

| Роль | Что делает | Типовой пример |
| --- | --- | --- |
| Stub resolver | Формирует запрос от имени приложения | libc/systemd-resolved |
| Recursive resolver | Ищет ответ и кэширует | `1.1.1.1`, resolver провайдера |
| Authoritative server | Хранит данные зоны | NS домена |

### Linux-команды

```sh
dig example.com
dig @1.1.1.1 example.com
dig +trace example.com
dig NS example.com
resolvectl status
tcpdump -ni any 'port 53'
```

### Практические примеры диагностики

#### Проверка resolver против authoritative data

```sh
dig @1.1.1.1 example.com
dig +trace example.com
```

Если публичный resolver отвечает `SERVFAIL`, а цепочка `+trace` ломается выше authoritative уровня, проблема не у клиента.

#### Проверка split DNS

Запросить имя через внутренний и внешний resolver и сравнить ответы.

### Реальные сетевые сценарии

#### Сценарий 1. Есть доступ по IP, но не по имени

Это типичный DNS-инцидент: резолвер не отвечает, сломан forwarder, firewall закрывает `53/udp` или вышестоящий резолвер настроен неверно.

#### Сценарий 2. Только часть клиентов получает неправильный IP

Часто причина в кэше конкретного рекурсивного резолвера или в split-horizon DNS (разные ответы для разных сетей).

### Типичные ошибки

- Путать recursive resolver и authoritative nameserver.
- Проверять DNS только через браузерный симптом без `dig`.
- Игнорировать TCP/53 fallback для больших ответов.
- Забывать о negative caching.

### Порядок диагностики

1. Проверить reachability до resolver по IP.
2. Проверить запрос к конкретному resolver через `@server`.
3. При необходимости выполнить `dig +trace`.
4. Проверить локальный кэш ОС и кэш recursive resolver.
5. Проверить firewall, MTU и TCP/53 fallback при больших ответах.

## Примеры

### Пример 1. Рекурсивное разрешение

Пользователь открывает `www.example.com`. Локальный клиент спрашивает резолвер провайдера или публичный resolver. Тот по кэшу или через итеративные запросы находит A/AAAA-запись.

### Пример 2. Проблема только по именам

```sh
ping 1.1.1.1        # работает
ping example.com    # не работает
dig example.com     # timeout
```

Вероятнее всего проблема связана не с общей IP-связностью, а с DNS.

### Пример 3. Авторитативная ошибка

`dig @1.1.1.1 example.com` возвращает `SERVFAIL`, а `dig NS example.com` показывает неверные NS или сломанную DNSSEC/зону. Это уже не проблема пользователя, а проблема домена.
