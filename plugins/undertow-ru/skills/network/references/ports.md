# Ports

Использовать этот раздел, когда нужно понять, какой сервис слушает соединение, почему процесс не принимает трафик, как firewall и NAT опираются на порты и чем отличаются well-known и ephemeral ports.

## Простое объяснение

Порт - это числовой идентификатор приложения внутри IP-узла. IP доставляет пакет на машину, а порт помогает доставить его нужному процессу.

## Техническое объяснение

Порты относятся к транспортному уровню и используются TCP и UDP. RFC 6335 фиксирует процедуры управления реестром сервисных имен и транспортных портов. Один и тот же номер может иметь разное значение в TCP и UDP.

## История

- Порты появились как способ демультиплексировать сетевые сервисы на одном хосте.
- По мере роста Интернета потребовался формальный IANA-реестр и правила управления им.

## Диапазоны портов

| Диапазон | Название | Типичное назначение |
| --- | --- | --- |
| 0-1023 | Well-known | Базовые сервисы, системные протоколы |
| 1024-49151 | Registered | Прикладные сервисы |
| 49152-65535 | Dynamic/Ephemeral | Временные клиентские порты |

## Порты и сокеты: подробно

### RFC и нормативная база

- RFC 6335 - Service Name and Transport Protocol Port Number Registry
- RFC 6056 - Recommendations for Transport Port Randomization

### Эфемерные порты в Linux

Диапазоны выше — классификация IANA. Linux по умолчанию берёт эфемерные клиентские порты из `32768–60999`, а не из `49152–65535`. Текущий диапазон:

```bash
sysctl net.ipv4.ip_local_port_range
```

### ASCII-схема сокета

```text
client 192.168.1.10:53124/tcp
  -> server 93.184.216.34:443/tcp
```

### Linux-команды

```sh
ss -lntup
lsof -i
nc -vz <host> <port>
tcpdump -ni any 'port 443'
nft list ruleset
```

### Практические примеры диагностики

#### Проверка bind/listen

Если сервис слушает только `127.0.0.1:443`, он недоступен извне, даже если firewall и routing корректны.

#### Проверка transport-specific порта

`53/udp` и `53/tcp` - не одно и то же. Нужно явно проверять нужный протокол.

### Реальные сетевые сценарии

#### Сценарий 1. DNS отвечает не всегда

Часть запросов проходит по UDP, а большие ответы требуют TCP/53 и ломаются на firewall.

#### Сценарий 2. PAT на границе

Эфемерные порты клиента становятся критичны для NAT и conntrack: именно ими различаются одновременные исходящие сессии.

### Типичные ошибки

- Проверять только номер порта без указания TCP/UDP.
- Считать "порт открыт" гарантией исправности приложения.
- Игнорировать bind-address.
- Забывать про ephemeral ports клиента и NAT.

### Порядок диагностики

1. Проверить, слушает ли процесс нужный IP:port/proto.
2. Проверить reachability к порту с клиента.
3. Проверить firewall/NAT правила.
4. Проверить особенности транспорта (TCP или UDP) и снять дамп трафика.

## Примеры

### Пример 1. Клиентский ephemeral port

Браузер открывает соединение:

```text
192.168.1.10:53124 -> 93.184.216.34:443/tcp
```

`53124` — временный порт клиента, `443` — стандартный (well-known) порт сервиса на сервере.

### Пример 2. DNS и два транспорта

`53/udp` - обычные короткие DNS-запросы.  
`53/tcp` - zone transfer, большие ответы, fallback.

### Пример 3. Почему `ss -lntup` важнее догадки

Пользователь говорит, что "nginx слушает 443". Проверка показывает, что процесс реально слушает только `127.0.0.1:443`, поэтому извне соединение не устанавливается.
