# Routing

Использовать этот раздел, когда нужно понять, как пакет выбирает путь, почему трафик уходит не туда, как работает default route и чем отличается статическая маршрутизация от динамической.

## Простое объяснение

Маршрутизация - это выбор следующего шага для пакета на пути к сети назначения.

## Техническое объяснение

Маршрутизатор сопоставляет IP-адрес назначения с таблицей маршрутов, выбирает самый специфичный префикс, а затем следующий узел (next hop) или напрямую подключённый интерфейс. Статические маршруты настраиваются вручную; динамические распространяются протоколами маршрутизации и меняются при изменении топологии.

## История

- Статическая маршрутизация появилась как базовый способ межсетевой связности.
- С ростом сетей потребовались динамические протоколы для масштабирования и сходимости.
- В учебных курсах Cisco статический маршрут и маршрут по умолчанию рассматриваются как простейшие формы маршрутизации.

## Routing: подробно

### RFC и нормативная база

- RFC 791 - IPv4 forwarding context
- RFC 1812 - Requirements for IP Version 4 Routers
- RFC 8200 - IPv6 forwarding context
- RFC 2328 - OSPFv2
- RFC 4271 - BGP-4

### Как принимается решение

```text
packet arrives
  -> inspect destination IP
  -> longest prefix match
  -> choose next hop or connected interface
  -> decrement TTL/Hop Limit
  -> forward
```

### Статическая и динамическая маршрутизация

| Тип | Плюсы | Минусы | Где использовать |
| --- | --- | --- | --- |
| Static | Простота, предсказуемость | Нет автоадаптации | Дом, small office, stub network |
| Dynamic | Сходимость, масштабирование | Сложность | Enterprise, ISP, multiple paths |

### ASCII-схема

```text
host A
  -> router R1
    -> router R2
      -> remote subnet
```

### Linux-команды

```sh
ip route
ip -6 route
ip route get 8.8.8.8
ip rule
traceroute 8.8.8.8
tracepath 1.1.1.1
```

### Практические примеры диагностики

#### Проверка longest prefix match

```sh
ip route get 10.20.30.40
```

Команда покажет, какой маршрут и какой `via` реально выбраны ядром.

#### Проверка asymmetry

Снять `tcpdump` на обоих uplink и посмотреть, не уходит ли запрос через один интерфейс, а ответ через другой.

### Реальные сетевые сценарии

#### Сценарий 1. Site-to-site VPN к филиалу

Нужен статический маршрут в удалённый префикс через туннельный интерфейс или адрес другой стороны туннеля.

#### Сценарий 2. Два провайдера на edge-router

Без маршрутизации по политикам (policy routing) или корректных метрик часть трафика может возвращаться через другой WAN и ломать firewall с отслеживанием состояния и NAT.

### Типичные ошибки

- Смотреть только наличие маршрута, а не конкретный route lookup.
- Игнорировать более специфичные префиксы.
- Забывать про маршрут возврата.
- Путать default route и route-policy.

### Порядок диагностики

1. Проверить таблицу маршрутов.
2. Выполнить `ip route get` для конкретной цели.
3. Проверить next hop и доступность соседнего роутера.
4. Проверить возвратный маршрут.
5. При multi-WAN проверить policy routing и асимметрию.

## Примеры

### Пример 1. Статический маршрут в филиал

```text
сеть филиала: 10.20.30.0/24
next hop: 192.168.100.2
```

Маршрут вручную добавляется на пограничный роутер. Пока топология стабильна, это простой и надежный вариант.

### Пример 2. Default route

Если у домашнего роутера нет знания о тысячах внешних сетей, он использует один маршрут по умолчанию в сторону провайдера.

### Пример 3. Асимметрия

Пакет уходит через один WAN, а ответ возвращается через другой и ломается stateful firewall/NAT.

### Частые команды

```sh
ip route
ip route get 8.8.8.8
traceroute 8.8.8.8
```
