# Mutual TLS

## 1. Что это такое

`mTLS` (mutual TLS) — режим, в котором не только сервер подтверждает свою подлинность клиенту, но и клиент предъявляет сертификат серверу. MDN отмечает, что аутентификация клиента по сертификату в вебе встречается редко, но применяется в специализированных сценариях.

## 2. Зачем это нужно

- усиливать защиту чувствительных административных интерфейсов и API;
- аутентифицировать соединения между сервисами;
- ограничивать доступ к управлению, не полагаясь только на пароль или токен;
- строить более строгую модель доверия.

## 3. Как это связано с VPN-инфраструктурой

- mTLS полезен для защищённого управления, внутренних API и трафика между сервисами;
- это актуально там, где панель, агенты или внутренние инструменты обмениваются чувствительными данными;
- mTLS — не то же самое, что обычный HTTPS: сервер должен доверять сертификату клиента.

## 4. Как это связано с Cloudflare

- при работе с Cloudflare приходится отдельно продумывать доверие на участке «браузер — Cloudflare» и на участке «Cloudflare или сервис — origin»;
- mTLS особенно полезен для связи с API на origin и для чувствительных административных путей;
- при публикации через Cloudflare важно понимать, где mTLS вообще применим: в браузере, на edge или между сервисами на стороне origin.

## 5. Как это связано с Remnawave

- Panel подключается к API Node (`NODE_PORT`) по mTLS: обе стороны предъявляют сертификаты, выпущенные внутренним CA Remnawave; ключи и сертификаты Node получает в `SECRET_KEY` (подробности — skill `remnawave`);
- для `Nginx Proxy Manager` mTLS — отдельный продвинутый слой, а не обычный переключатель HTTPS.

## 6. Типовые ошибки

- путать mTLS с обычным TLS;
- ожидать, что браузерный вход всегда нормально работает с клиентскими сертификатами;
- не разделять публичную веб-публикацию и аутентификацию внутренних сервисов;
- забывать, что обе стороны должны доверять цепочке сертификатов.

## 7. Диагностика

1. Проверить, требуется ли клиентский сертификат.
2. Проверить доверие к сертификатам на обеих сторонах.
3. Отделить общий сбой TLS от сбоя аутентификации клиента.
4. Проверить, на каком участке пути применяется mTLS.
5. Не смешивать HTTPS для браузера и mTLS между сервисами.

## 8. Практические примеры

- Защита внутреннего административного интерфейса или API за reverse proxy клиентским сертификатом.
- Разбор, почему обычный вход через браузер не проходит к маршруту, защищённому mTLS.
- Объяснение, где mTLS уместен для управления, а где достаточно обычного HTTPS.
- Взаимодействие внутренних компонентов с аутентификацией по клиентскому сертификату.

## 9. Чек-лист

- Уточнить, нужен ли публичный HTTPS или именно взаимная аутентификация.
- Проверить, кто клиент и кто сервер в модели доверия.
- Не путать mTLS с «просто включённым TLS».
- При необходимости перейти к `tls.md`, `https.md` и `reverse-proxy.md`.
