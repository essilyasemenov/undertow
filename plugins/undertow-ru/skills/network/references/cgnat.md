# CGNAT

Использовать этот раздел, когда у пользователя есть Интернет, но нет собственного публичного IPv4 и не работают входящие подключения, проброс портов или некоторые P2P/VPN-сценарии.

## Простое объяснение

CGNAT - это NAT у провайдера. Абонент получает не уникальный публичный IPv4, а адрес из общего пула или частного пространства, а затем делит один внешний адрес с другими абонентами.

## Техническое объяснение

CGNAT стандартизован с эксплуатационной стороны в RFC 6888. Это масштабная операторская NAPT-платформа с большими таблицами трансляций, логированием и ограничениями по портам/таймаутам.

## История

- Массово распространился из-за исчерпания публичного IPv4.
- Стал компромиссом между потребностью сохранить IPv4-доступность и высокой стоимостью публичных адресов.

## Основные последствия

- нет прямого inbound IPv4 без специальных услуг провайдера;
- сложнее self-hosting;
- сложнее корреляция логов;
- возможны ограничения по числу одновременных сессий/портов.

## CGNAT: подробно

### RFC и нормативная база

- RFC 6598 - Shared Address Space `100.64.0.0/10`
- RFC 6888 - Common Requirements for Carrier-Grade NATs

### Как распознать CGNAT

- WAN-адрес роутера не совпадает с внешним IP.
- WAN получает RFC 1918 адрес или `100.64.0.0/10`.
- Port forward на домашнем роутере не дает входящей доступности.

### ASCII-схема

```text
LAN host 192.168.1.10
  -> home NAT
100.64.10.5
  -> ISP CGNAT
198.51.100.25
  -> Internet
```

### Linux-команды

```sh
ip addr
ip route
curl -4 ifconfig.me
traceroute 1.1.1.1
```

### Практические примеры диагностики

#### Сравнение WAN IP и внешнего IP

```sh
curl -4 ifconfig.me
```

Если внешний IP отличается от WAN на роутере, велика вероятность промежуточного NAT.

#### Проверка недоступного port forward

Если сервис внутри LAN слушает, локальный DNAT настроен, но извне недоступен и WAN не публичный - это типичный CGNAT.

### Реальные сетевые сценарии

#### Сценарий 1. Домашний VPN-сервер не доступен с мобильной сети

Причина может быть не в WireGuard-конфиге, а в отсутствии собственного публичного IPv4.

#### Сценарий 2. Жалобы на репутацию внешнего IP

Под одним IP могут жить десятки или сотни абонентов, поэтому блок-листы и rate limits иногда затрагивают невиновных пользователей.

### Типичные ошибки

- Пытаться исправить CGNAT обычным port forward на своем роутере.
- Путать частный WAN-адрес со "статическим публичным".
- Искать причину только в firewall LAN-сервера.

### Порядок диагностики

1. Проверить WAN IP.
2. Сравнить его с внешним IP, видимым из Интернета.
3. Уточнить у провайдера наличие CGNAT и услуги публичного IPv4.
4. При необходимости перейти на IPv6, reverse tunnel или VPS.

## Примеры

### Пример 1. Проброс порта не работает

Пользователь настроил `443 -> 192.168.1.20:443` на домашнем роутере, но снаружи сервис недоступен. WAN роутера имеет `100.64.23.10`, а внешний сервис показывает `198.51.100.77`. Это типичный признак CGNAT.

### Пример 2. VPN-сервер дома

Домашний WireGuard-сервер не принимает входящие пакеты из Интернета при наличии CGNAT. Решения:

- запросить публичный IPv4;
- использовать IPv6;
- поднять сервер на VPS и строить tunnel к нему.

### Частый вопрос

#### Почему веб-сайты могут работать, а входящие подключения нет?

Потому что исходящие соединения CGNAT пропускает через свои таблицы трансляции, а входящее соединение, для которого не создана запись в таблице, некуда доставить.
