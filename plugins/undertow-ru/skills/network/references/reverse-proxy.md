# Reverse Proxy

## 1. Что это такое

`Reverse proxy` принимает запрос клиента, передаёт его на сервер за собой (upstream) и возвращает ответ клиенту. Официальная документация NGINX описывает это как базовую конфигурацию проксирования: передачу запросов, изменение заголовков запроса и управление буферизацией.

## 2. Зачем это нужно

- публиковать внутренние сервисы через одну внешнюю точку входа;
- скрывать внутреннюю топологию origin;
- централизованно завершать TLS и настраивать редиректы;
- направлять трафик на разные внутренние сервисы.

## 3. Как это связано с VPN-инфраструктурой

- интерфейсы управления VPN обычно публикуются через reverse proxy;
- это касается веб-интерфейса панели, страниц подписок, API и dashboard;
- reverse proxy становится границей между Интернетом и внутренними сервисами.

## 4. Как это связано с Cloudflare

- при публикации через Cloudflare reverse proxy обычно стоит на стороне origin;
- CDN и reverse proxy — разные слои: доставка на edge и обработка запросов на origin;
- ошибки чаще всего возникают на стыке `Cloudflare -> NGINX/NPM -> upstream`.

## 5. Как это связано с Remnawave

- документация `Remnawave` требует публиковать панель только через reverse proxy и перечисляет варианты: Caddy, Nginx, Traefik, Angie;
- reverse proxy скрывает порты backend (`127.0.0.1:3000`) и завершает HTTPS.

## 6. Типовые ошибки

- публиковать backend напрямую, в обход reverse proxy;
- путать reverse proxy с CDN;
- ломать заголовки или схему запроса при передаче на upstream;
- забывать, что буферизация и пересылка меняют поведение приложения;
- не понимать, где заканчивается TLS и начинается незашифрованный HTTP до upstream.

## 7. Диагностика

1. Проверить доступность самого reverse proxy.
2. Проверить, отвечает ли upstream напрямую, без proxy.
3. Проверить маршрутизацию по имени хоста и пути.
4. Проверить заголовки и схему (`http`/`https`) между слоями.
5. Проверить, не в DNS, firewall или CDN ли первопричина.

## 8. Практические примеры

- Публикация панели `Remnawave` за `NGINX`.
- Разбор ошибок `502/504`, когда backend не слушает ожидаемый порт.
- Сравнение прямого доступа к backend и доступа через Cloudflare + reverse proxy.

## 9. Чек-лист

- Определить, есть ли цепочка `клиент -> CDN -> reverse proxy -> приложение`.
- Уточнить схему, порт и маршрутизацию по имени хоста для upstream.
- Не сводить reverse proxy, TLS и firewall в одну причину.
- Для Nginx Proxy Manager проверить, не открыт ли backend в обход proxy.
- При необходимости перейти к `https.md`, `tls.md` и `firewall.md`.
