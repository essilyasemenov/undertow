# Firewall

## 1. Что это такое

`Firewall` — слой фильтрации сетевого трафика и применения политик доступа. На Linux-хостах он реализуется через `nftables` (и надстройки вроде `ufw`) и управляет доступом между интерфейсами, зонами и сервисами.

## 2. Зачем это нужно

- сокращать поверхность атаки;
- разрешать только нужные входящие и исходящие потоки;
- разделять зоны LAN, WAN и сервисов;
- не допускать случайной публикации портов панели, API и backend.

## 3. Как это связано с VPN-инфраструктурой

- неточная политика firewall ломает VPN-инфраструктуру и по безопасности, и по доступности;
- открытые административные порты, неверные пробросы и слишком широкие разрешающие правила создают лишний риск;
- firewall определяет, какие пути управления и передачи данных реально доступны.

## 4. Как это связано с Cloudflare

- Cloudflare не заменяет локальный firewall на origin;
- даже при публикации через edge firewall origin должен ограничивать прямой доступ;
- firewall особенно важен, если IP origin доступен напрямую.

## 5. Как это связано с Remnawave

- docs Remnawave требуют не публиковать сервисы напрямую: в официальном `docker-compose` порты Panel (`3000`, `3001`) и Postgres (`6767`) привязаны к `127.0.0.1`;
- `NODE_PORT` на Node разрешать только с IP Panel;
- для `Nginx Proxy Manager` и других reverse proxy firewall гарантирует, что backend доступен только через proxy.

## 6. Docker и ufw

Документация Docker предупреждает: Docker и `ufw` несовместимы. Трафик к опубликованным портам контейнеров (`ports:` в compose) Docker перенаправляет в таблице `nat` раньше, чем он доходит до цепочек `INPUT` и `OUTPUT`, которые использует `ufw`. Поэтому правило `ufw deny` такой порт не закрывает.

- Порт, который не должен быть доступен извне, публиковать на `127.0.0.1` (как в официальном compose Remnawave) или не публиковать вовсе.
- Контейнеры с `network_mode: host` (так работает Remnawave Node) не используют проброс Docker; их порты фильтрует обычный firewall хоста.

## 7. Типовые ошибки

- открывать лишние порты «на всякий случай»;
- считать CDN или reverse proxy заменой firewall;
- разрешать прямой доступ к портам backend или панели;
- не различать публикацию наружу и доступ между узлами внутри сети;
- менять firewall и не проверять обратный путь трафика;
- закрывать порт контейнера через `ufw` и считать его закрытым.

## 8. Диагностика

1. Определить, какой трафик должен быть разрешён и между какими зонами.
2. Проверить, доступен ли сервис локально и недоступен ли только извне.
3. Проверить, не открыт ли origin в обход proxy или CDN.
4. Отдельно смотреть firewall хоста, firewall роутера и фильтрацию на edge.
5. Проверить ожидаемый путь и нежелательный прямой путь.

## 9. Практические примеры

- Ограничение доступа к Remnawave Panel только через reverse proxy.
- Ограничение origin `Remnawave` так, чтобы публично работала только нужная веб-точка входа.
- Проверка, что backend за `Nginx Proxy Manager` не принимает прямые соединения из Интернета.

## 10. Чек-лист

- Определить, где именно стоит firewall: хост, роутер, облачный edge.
- Проверить ожидаемый путь и нежелательный прямой путь.
- Разделить проблему открытости сервиса и проблему приложения.
- Для Cloudflare и reverse proxy отдельно проверить, не доступен ли origin напрямую.
- При необходимости перейти к `linux-networking.md` и `reverse-proxy.md`.
