# TCP/IP

Использовать этот раздел, когда нужно объяснить, как Интернет работает на практике, без избыточной абстракции OSI.

## Простое объяснение

TCP/IP - это семейство протоколов, на котором реально работает Интернет. IP отвечает за адресацию и доставку пакетов между сетями, а TCP и UDP - за передачу данных приложениям.

## Техническое объяснение

Стек TCP/IP обычно рассматривают как модель из 4 уровней: канальный (Link), межсетевой (Internet), транспортный (Transport) и прикладной (Application). Инкапсуляция идёт сверху вниз, а маршрутизаторы принимают решения в основном на межсетевом уровне, не разбирая прикладные данные.

## История

- Истоки - ARPANET и ранние интернет-эксперименты.
- MDN отмечает, что история Интернета начинается в 1960-х и переходит к публичной инфраструктуре в 1980-х.
- Современная спецификация TCP собрана в RFC 9293, IPv6 - в RFC 8200.

## Компоненты

- Link: Ethernet, Wi-Fi
- Internet: IPv4, IPv6, ICMP
- Transport: TCP, UDP
- Application: DNS, HTTP, SMTP, SSH

## Схема инкапсуляции

```text
HTTP request
  -> TCP segment
    -> IP packet
      -> Ethernet frame
```

## Типичные ошибки

- Путать TCP/IP только с TCP. IP и TCP - не одно и то же.
- Считать, что IP гарантирует доставку и порядок. Это делает не IP.
- Игнорировать транспортный и прикладной слой при рабочем маршруте.

## Диагностика

- Проверить IP-адрес и маршрут
- Проверить reachability до удаленного IP
- Проверить нужный transport protocol и порт
- Проверить прикладной протокол

## Лучшие практики

- Объяснять любую проблему цепочкой `application -> transport -> IP -> link`.
- Различать адресацию, маршрутизацию и надежность доставки.
- Для любого сервиса фиксировать: какой IP, какой transport, какой port, какой путь возврата.

## TCP/IP: подробно

### Роль раздела

Этот раздел описывает реальный Internet protocol suite. Поведение конкретных транспортных протоколов, MTU и DNS вынесено в отдельные разделы, чтобы не дублировать детали.

### RFC и нормативная база

- RFC 791 - IPv4
- RFC 792 - ICMP for IPv4
- RFC 1122 - Host Requirements
- RFC 1123 - Host Requirements for Internet applications
- RFC 8200 - IPv6
- RFC 9293 - TCP
- RFC 768 - UDP

### Архитектура стека

| Уровень TCP/IP | Назначение | Примеры |
| --- | --- | --- |
| Application | Прикладная логика | DNS, HTTP, SSH |
| Transport | Доставка приложению | TCP, UDP |
| Internet | Межсетевая доставка | IPv4, IPv6, ICMP |
| Link | Локальная доставка | Ethernet, Wi-Fi |

### ASCII-схема инкапсуляции

```text
application payload
  -> TCP/UDP header
    -> IP header
      -> Ethernet/Wi-Fi frame
```

### ASCII-схема пути пакета

```text
client
  -> local switch/ap
  -> router/default gateway
  -> upstream routers
  -> destination server
```

### Реальные сетевые сценарии

#### Сценарий 1. Веб работает по IPv4, но не по IPv6

Это не "поломка TCP/IP вообще", а частичный отказ Internet layer для одного семейства адресов.

#### Сценарий 2. VPN поднят, но часть приложений не выходит наружу

Нужно разделять:

- IP-маршрут через туннель;
- DNS-путь;
- TCP/UDP-поведение приложения;
- MTU в туннеле.

### Типичные ошибки на практике

- Путать стек TCP/IP с одним TCP.
- Считать IP надежным транспортом.
- Игнорировать различие между адресацией, маршрутизацией и приложением.
- Пытаться диагностировать HTTP, не проверив IP-route и transport.

### Порядок диагностики

1. Проверить IP-адреса на интерфейсах.
2. Проверить таблицу маршрутов и route lookup.
3. Проверить reachability до IP без участия DNS.
4. Проверить нужный transport и порт.
5. Проверить прикладной протокол.

## Примеры

### Сценарий 1. Доступ к веб-сайту

```text
браузер
  -> DNS определяет IP
  -> TCP устанавливает соединение с 443/tcp
  -> IP доставляет пакеты через маршрутизаторы
  -> HTTP/TLS обмениваются данными приложения
```

### Сценарий 2. Почему ping не равен "сайт работает"

- `ping` проверяет IP-достижимость, а не HTTP.
- Сайт может не открываться из-за DNS, TCP/443, TLS, reverse proxy или приложения.

### Частые команды

```sh
ping 1.1.1.1
traceroute 1.1.1.1
ss -tn state established
curl -I https://example.com
dig example.com
```

### Частый реальный кейс

Пользователь говорит: "VPN подключен, но сайт не грузится".

Разбор:

- IP-туннель может быть поднят.
- TCP route back может быть сломан.
- DNS может идти не через нужный resolver.
- MTU может резать большие TCP-сегменты.
