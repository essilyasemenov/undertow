# Load Balancing

## 1. Что это такое

`Load balancing` (балансировка нагрузки) — распределение трафика между несколькими экземплярами backend для повышения доступности, масштабируемости и устойчивости. Документация NGINX описывает балансировку как распределение трафика между серверами приложений ради пропускной способности, меньшей задержки и отказоустойчивости.

## 2. Зачем это нужно

- не перегружать один backend;
- повышать отказоустойчивость;
- масштабировать приложения и панели;
- повышать доступность публичных веб-сервисов и API.

## 3. Как это связано с VPN-инфраструктурой

- веб-интерфейсам и API управления VPN может понадобиться балансировка;
- страницы подписок, dashboard и сервисы за reverse proxy выигрывают от переключения на резерв (failover);
- балансировка особенно полезна там, где важны доступность и плавное масштабирование.

## 4. Как это связано с Cloudflare

- доставка через edge Cloudflare и распределённая инфраструктура тесно связаны с устойчивостью;
- материалы Cloudflare прямо связывают надёжность CDN с распределением трафика и переключением на резерв;
- важно различать распределение трафика anycast-edge и балансировку на уровне приложения.

## 5. Как это связано с Remnawave

- Panel масштабируется переменной `API_INSTANCES` (по умолчанию `1`); в `remnawave/backend` есть также `docker-compose-advanced-prod.yml`, где REST API вынесен в отдельные масштабируемые сервисы (подробности — skill `remnawave`);
- `Nginx Proxy Manager` и `NGINX` — типичное место, где на практике настраивается балансировка между upstream.

## 6. Типовые ошибки

- путать балансировку нагрузки и anycast;
- ожидать привязки сессии к одному backend (session stickiness) без явной настройки;
- балансировать сервис, backend которого не рассчитан на несколько экземпляров;
- забывать, что проверки состояния и логика переключения меняют наблюдаемое поведение.

## 7. Диагностика

1. Проверить, отвечает один backend или несколько.
2. Уточнить, есть ли привязка сессии.
3. Проверить ожидания по переключению на резерв и по проверкам состояния.
4. Разделить распределение на edge и балансировку на уровне приложения.
5. Проверить, не в reverse proxy ли первопричина.

## 8. Практические примеры

- Балансировка нескольких экземпляров веб-backend через `NGINX`.
- Разбор, почему запросы к одной панели дают разный результат.
- Объяснение разницы между anycast-edge Cloudflare и балансировкой upstream в NGINX.
- Проверка переключения на резерв при отказе одного origin.

## 9. Чек-лист

- Уточнить, о чём речь: о распределении через anycast/CDN или о балансировке на уровне приложения.
- Определить, есть ли группа upstream и переключение на резерв.
- Проверить, нужна ли привязка сессии (session affinity).
- При необходимости перейти к `reverse-proxy.md`, `cdn.md` и `anycast.md`.
