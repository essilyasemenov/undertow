# OSI Model

Использовать этот раздел, когда нужно разложить сетевую проблему по уровням и не смешивать физическую неисправность, IP-маршрутизацию, DNS и прикладной протокол в одну причину.

## Простое объяснение

OSI - это учебная модель, которая делит сетевое взаимодействие на 7 уровней, чтобы было проще понять, где именно ломается связь.

## Техническое объяснение

OSI не описывает Интернет "как он реализован байт в байт". Это абстракция ISO, которая помогает отделить физическую передачу сигнала, канальную доставку кадров, межсетевую доставку пакетов, транспорт, сеансы, представление данных и приложения. В реальной эксплуатации стек TCP/IP проще, но диагностическая ценность OSI остается высокой.

## История

- Разработана ISO как эталонная модель межсистемного взаимодействия.
- Исторически стала общим языком для инженеров и преподавания сетей.
- Современный Интернет строится не строго по OSI, а ближе к TCP/IP, но термины L2, L3, L4 и L7 используются повсеместно.

## Уровни и типовые примеры

| Уровень | Что делает | Примеры |
| --- | --- | --- |
| L1 Physical | Передает биты | кабель, оптика, радиоканал |
| L2 Data Link | Передает кадры в пределах сегмента | Ethernet, Wi-Fi, MAC |
| L3 Network | Доставляет пакеты между сетями | IPv4, IPv6, ICMP |
| L4 Transport | Доставляет данные процессам | TCP, UDP |
| L5 Session | Управляет логикой сеанса | части SMB, RPC, TLS-сеанс в прикладном контексте |
| L6 Presentation | Представление и кодирование данных | TLS, ASN.1, JSON encoding в практическом смысле |
| L7 Application | Логика приложения | HTTP, DNS, SMTP |

## Принцип работы

```text
приложение
  -> формирует полезные данные
  -> передает их вниз по стеку
  -> каждый уровень добавляет свой заголовок
  -> на приемнике заголовки снимаются в обратном порядке
```

## Основные компоненты и инструменты

- L1: `ethtool`, индикация линка, SFP/кабельные тесты
- L2: `ip link`, `bridge`, `arp`, `tcpdump -e`
- L3: `ip addr`, `ip route`, `ping`, `traceroute`
- L4: `ss -lntup`, `nc`, `tcpdump 'tcp or udp'`
- L7: `curl`, `dig`, `openssl s_client`

## Типичные ошибки и заблуждения

- "Ping работает, значит сеть исправна" - нет, может быть сломан DNS, TCP/443 или MTU.
- "OSI точно соответствует Интернету" - нет, это модель, а не буквальная реализация.
- "DNS - это всегда отдельный слой" - практически DNS относят к приложению, хотя он зависит от L3/L4.

## Лучшие практики

- Диагностировать снизу вверх: link -> L2 -> IP -> маршрут -> transport -> application.
- Формулировать проблему по слоям: "нет carrier", "нет ARP", "нет default route", "TCP SYN уходит без SYN-ACK", "DNS отвечает NXDOMAIN".
- Использовать OSI как язык общения, а не как догму.

## OSI: подробно

### Роль раздела

Этот раздел нужен не для описания конкретного интернет-стандарта, а для методического разложения неисправности по слоям. Детали TCP/IP, DNS, MTU, NAT и routing вынесены в профильные разделы.

### RFC и нормативная база

- Прямого RFC для модели OSI нет: это эталонная модель ISO.
- RFC 1122 - Host Requirements и практическая модель уровней в стеке TCP/IP.
- RFC 1123 - дополнительные требования к хостам и прикладным протоколам.

### Соотношение OSI и TCP/IP

| OSI | TCP/IP | Что реально диагностируется |
| --- | --- | --- |
| L7-L5 | Application | DNS, HTTP, TLS, SSH |
| L4 | Transport | TCP, UDP, порты, retransmission |
| L3 | Internet | IPv4, IPv6, routing, ICMP |
| L2-L1 | Link | Ethernet, Wi-Fi, VLAN, carrier |

### ASCII-схема

```text
L7  Application   -> HTTP, DNS, SMTP
L6  Presentation  -> TLS, кодирование данных
L5  Session       -> управление логикой обмена
L4  Transport     -> TCP, UDP, ports
L3  Network       -> IPv4, IPv6, routing
L2  Data Link     -> Ethernet, Wi-Fi, MAC, VLAN
L1  Physical      -> кабель, оптика, радио
```

### Практическая схема диагностики

```text
нет доступа к сервису
  -> есть ли carrier/L1
  -> есть ли соседство и VLAN/L2
  -> есть ли адрес, маршрут и gateway/L3
  -> есть ли TCP/UDP обмен/L4
  -> работает ли DNS/TLS/HTTP/L7
```

### Linux-команды

```sh
ip link
ip addr
bridge link
ip route
ping -c 3 8.8.8.8
traceroute 8.8.8.8
ss -lntup
tcpdump -ni any
curl -I https://example.com
dig example.com
```

### Реальные сценарии

#### Сценарий 1. "Wi-Fi есть, сайты не открываются"

- L1/L2: ассоциация есть.
- L3: клиент получил адрес, но нет default route.
- Вывод: проблема уровня L3, а не "сломанный Интернет вообще".

#### Сценарий 2. "IP пингуется, имя не резолвится"

- L3 исправен.
- L7 для DNS сломан.
- Вывод: не нужно начинать с кабеля или маршрута.

#### Сценарий 3. "Сервис слушает локально, но недоступен извне"

- L4 на хосте может быть исправен.
- Проблема может быть на границе L3/L4: firewall, NAT, обратный маршрут.

### Типичные ошибки

- Пытаться объяснить любой сбой только одним слоем.
- Считать OSI буквальной картой современного Интернета.
- Делать вывод "сеть исправна" только по `ping`.
- Разбирать DNS раньше проверки IP-адреса и маршрута.

### Порядок диагностики

1. Проверить физическое состояние интерфейса и carrier.
2. Проверить L2-смежность: MAC, bridge, VLAN, ARP/NDP.
3. Проверить L3: адрес, префикс, выбор маршрута, шлюз.
4. Проверить L4: SYN/SYN-ACK, запрос и ответ UDP, слушающий сокет.
5. Проверить L7 конкретным клиентом: `curl`, `dig`, `openssl s_client`.

## Примеры

### Сценарий 1. "Wi-Fi есть, Интернет не работает"

Разбор по слоям:

1. L1/L2: клиент ассоциирован с Wi-Fi, link есть.
2. L3: клиент получил адрес `192.168.1.20/24`, но gateway неверный.
3. L4/L7: не проверяем до исправления L3.

Вывод: симптом выглядел как "Интернет умер", но первопричина - ошибка адресации.

### Сценарий 2. "Пингуется IP, но сайт не открывается"

```text
ping 1.1.1.1            -> работает
dig example.com         -> timeout
curl https://1.1.1.1    -> TCP есть, но это не равно доступности нужного сайта
```

Вывод: вероятнее всего проблема в L7/L4 для DNS, а не в базовой IP-связности.

### Сценарий 3. "Сервис слушает, но извне недоступен"

- L4 локально: `ss -lntp` показывает `0.0.0.0:443`
- L3: маршрут наружу есть
- L4/L3 на границе: firewall или NAT не пропускает входящий SYN

### Частые вопросы

#### С чего начинать диагностику?

С самого нижнего подтверждаемого уровня. Если нет линка, DNS бессмысленно разбирать.

#### Когда модель OSI вредна?

Когда ее используют как догму и игнорируют реальные стековые особенности TCP/IP, QUIC, NAT и firewall state.
