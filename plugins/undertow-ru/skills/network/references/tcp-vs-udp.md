# TCP vs UDP

Использовать этот раздел, когда нужно выбрать транспортный протокол, объяснить поведение сервиса или понять, почему один поток чувствителен к потерям, а другой - к задержкам.

## Простое объяснение

TCP делает доставку надежной и упорядоченной. UDP делает доставку быстрой и простой, но без гарантий.

## Техническое объяснение

TCP — транспорт с установкой соединения: рукопожатие, порядковые номера, подтверждения, повторная передача, управление потоком и перегрузкой. UDP — протокол датаграмм без установки соединения, с минимальным заголовком и без встроенных гарантий доставки или порядка.

## История

- UDP стандартизован в RFC 768.
- TCP исторически был RFC 793, а актуальная консолидированная спецификация - RFC 9293.
- Рост real-time трафика сделал компромисс TCP/UDP особенно заметным в VoIP, видеостриминге и DNS.

## Сравнение

| Свойство | TCP | UDP |
| --- | --- | --- |
| Соединение | Есть | Нет |
| Порядок доставки | Гарантируется | Не гарантируется |
| Повтор потерянных данных | Есть | Нет |
| Контроль перегрузки | Есть | Нет на уровне протокола |
| Задержка старта | Выше | Ниже |
| Типичные сценарии | HTTPS, SSH, SMTP | DNS, VoIP, gaming, telemetry |

## Типичные заблуждения

- "UDP лучше TCP, потому что быстрее" - не всегда; для критичных данных потери могут сделать приложение хуже.
- "UDP не имеет портов" - имеет, RFC 768 определяет source и destination port.
- "TCP всегда медленнее" - при нормальной сети TCP может быть оптимальным за счет надежности и управления потоком.

## Диагностика

- TCP: смотреть рукопожатие, повторные передачи, окно и сбросы (RST).
- UDP: смотреть, отправлен ли и получен ли пакет, потери, джиттер и повторы на уровне приложения.

## TCP и UDP: подробно

### RFC и нормативная база

- RFC 768 - UDP
- RFC 8085 - UDP Usage Guidelines
- RFC 9293 - TCP

### Сравнение: детали

| Свойство | TCP | UDP |
| --- | --- | --- |
| Тип | Connection-oriented | Connectionless |
| Гарантия порядка | Да | Нет |
| Повтор потерянных данных | Да | Нет |
| Контроль перегрузки | Встроен | На уровне приложения или отсутствует |
| Типичное использование | HTTPS, SSH, SMTP | DNS, VoIP, telemetry, media |

### ASCII-схема TCP

```text
client SYN
  -> server SYN-ACK
    -> client ACK
      -> data
        -> ACK/retransmission/window control
```

### ASCII-схема UDP

```text
client datagram
  -> network
    -> server datagram receive or loss
```

### Linux-команды

```sh
ss -tn
ss -un
tcpdump -ni any 'tcp port 443'
tcpdump -ni any 'udp port 53'
nc -vz example.com 443
dig @1.1.1.1 example.com
```

### Практические примеры диагностики

#### TCP: SYN уходит, SYN-ACK не приходит

```sh
tcpdump -ni any 'tcp[tcpflags] & (tcp-syn|tcp-ack) != 0 and host <server-ip>'
```

Возможные причины:

- firewall;
- неверный DNAT;
- маршрут возврата;
- сервис не слушает.

#### UDP: запрос ушел, ответа нет

```sh
tcpdump -ni any 'udp and host <server-ip>'
dig @<server-ip> example.com
```

Возможные причины:

- packet loss;
- фрагментация;
- ACL/firewall;
- приложение не отвечает.

### Реальные сетевые сценарии

#### Сценарий 1. DNS работает нестабильно только по UDP

Маленькие ответы проходят, большие режутся из-за MTU/firewall, а TCP fallback спасает часть запросов.

#### Сценарий 2. Голос в звонке рвется, хотя HTTPS работает

UDP-медиатрафик чувствителен к jitter и loss, а TCP-веб-трафик компенсирует потери повторами.

### Типичные ошибки

- Называть UDP "сломанным TCP без handshake".
- Считать, что отсутствие handshake означает отсутствие портов и состояния в приложении.
- Ожидать от UDP встроенной надежности.
- Оценивать real-time трафик только по throughput.

### Порядок диагностики

1. Уточнить, какой transport использует сервис.
2. Проверить listen socket или факт генерации датаграмм.
3. Снять capture и увидеть направление обмена.
4. Для TCP искать проблемы рукопожатия, повторные передачи и сбросы.
5. Для UDP искать потерю, ACL, MTU и логи приложения.

## Примеры

### Пример 1. DNS lookup

- Клиент отправляет короткий UDP-запрос на `53/udp`.
- Если ответ слишком большой или требуется zone transfer, возможен TCP.

### Пример 2. Видеозвонок

Потеря части пакетов лучше, чем накопление задержки из-за повторов. Поэтому медиапотоки часто идут поверх UDP.

### Пример 3. SSH

SSH требует корректной последовательности байт и надежности. Потерянный байт ломает сессию, поэтому TCP подходит лучше.

### Типичный инцидент

Сервис мониторинга отправляет telemetry по UDP и часть событий пропадает при перегрузке WAN. Это не "сломанный сервер" по умолчанию - это может быть ожидаемое поведение ненадежного транспорта под нагрузкой.
