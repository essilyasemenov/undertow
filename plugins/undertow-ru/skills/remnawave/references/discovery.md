# Обнаружение фактической установки

Пути, имена контейнеров и файлов в остальных справочниках взяты из официальной установки: `/opt/remnawave`, `/opt/remnanode`, `/opt/remnawave/subscription`, контейнеры `remnawave` и `remnanode`. На реальном сервере установка может отличаться: другой каталог, переименованные контейнеры, свой compose-файл, отдельный reverse proxy, собственные скрипты.

Поэтому перед командами, которые зависят от пути или имени контейнера, сначала выяснить фактическое расположение, если пользователь не подтвердил, что установка официальная. Потом подставлять в команды найденные значения.

Все команды ниже только читают, ничего не меняют. Выполняет их пользователь на своём сервере. Если Claude Code запущен на другой машине, локальный диск не обыскивать: файлов Remnawave там нет, а в домашнем каталоге лежат чужие для задачи данные.

## Контейнеры и образы

```bash
docker ps --format 'table {{.Names}}\t{{.Image}}\t{{.Status}}\t{{.Ports}}'
```

По колонке `Image` видно, какой контейнер Panel (`remnawave/backend`), Node (`remnawave/node`), Subscription Page, база и кэш, и какой у них тег. Имя из колонки `Names` подставлять в `docker exec <имя> ...` вместо `remnawave` и `remnanode`.

## Где лежат compose-файлы

Все compose-проекты на сервере и пути к их файлам:

```bash
docker compose ls
```

Каталог и compose-файл конкретного контейнера:

```bash
docker inspect <имя_контейнера> --format '{{ index .Config.Labels "com.docker.compose.project.working_dir" }}'
docker inspect <имя_контейнера> --format '{{ index .Config.Labels "com.docker.compose.project.config_files" }}'
```

Найденный каталог использовать вместо `/opt/remnawave` или `/opt/remnanode`. Если меток нет, контейнер запущен не через Docker Compose, и команды `docker compose ...` к нему неприменимы.

## Переменные окружения

Только имена переменных, без значений: в значениях секреты.

```bash
docker inspect <имя_контейнера> --format '{{range .Config.Env}}{{println .}}{{end}}' | cut -d= -f1 | sort
```

Значение конкретной несекретной переменной (например, `SUB_PUBLIC_DOMAIN`, `FRONT_END_DOMAIN`):

```bash
docker inspect <имя_контейнера> --format '{{range .Config.Env}}{{println .}}{{end}}' | grep '^SUB_PUBLIC_DOMAIN='
```

Не просить пользователя присылать целиком `.env` или вывод с `APP_SECRET`, паролями, `SECRET_KEY`, токенами.

## Порты и reverse proxy

```bash
ss -lntp
```

Показывает, кто слушает `80`/`443` (reverse proxy), порты Panel (по умолчанию `127.0.0.1:3000`) и `NODE_PORT` на Node. Если reverse proxy тоже в контейнере, он виден в `docker ps`.

## Установки без Docker или со своими скриптами

```bash
systemctl list-units --type=service | grep -iE 'remna|xray|caddy|nginx'
```

```bash
find / -xdev \( -name '*compose*.y*ml' -o -name '.env' \) -path '*remna*' 2>/dev/null
```

Если установка нестандартная, команды из остальных справочников давать как шаблон и явно говорить, что они рассчитаны на официальную установку.

## Что делать с результатом

- Совпадает с официальной установкой — пользоваться остальными справочниками как есть.
- Отличается — подставлять фактические каталоги и имена контейнеров; про отличия (свой compose, другой reverse proxy) говорить, что docs.rw их не описывает.
- Не менять файлы пользователя и не перезапускать сервисы, пока он не подтвердил план.
